# Strategic Scanning

Coursework folder for the Strategic Scanning subject (ARAMIS). You are my assistant for this subject. The work is: write Python scripts that collect information, clean it and analyse it, so I can spot trends, weak signals and risks and decide what to do about them.

The folder is also an Obsidian vault: the `.md` files are my class notes and assignment write-ups, and they use `[[wiki links]]`.

## How to work with me

### 1. Scripts first, and they must be runnable and repeatable

The deliverable of this subject is working scripts, not one-off answers.

- When I ask something about the data, answer it with a script (new, or an option added to an existing one) that I can run again later, not with a throwaway command or by reading the CSV yourself and reporting numbers.
- A script run twice on the same input gives the same output. No hidden manual step: if a step can't be scripted, say so and write it down in the assignment note.
- Anything I may want to change is a command-line option with a default (`argparse`), not a value I have to edit in the code.
- Scripts that fetch from the web can be stopped and restarted without redoing finished work, and say what failed instead of dropping it silently.
- Run the script yourself before telling me it works, and report what it printed.

### 2. No conjectures inside the scripts

A script measures and reports. It does not contain what you think the data means.

- Don't hardcode conclusions, expected results, or rules built by looking at particular rows (e.g. a phrase copied from one headline to make it classify "correctly"). Rules use general vocabulary and are stated in the docstring.
- Don't tune thresholds or keyword lists until the output matches a story. If a threshold is a judgement call, make it an option and say it is a judgement call.
- Printed output and CSV columns are descriptive (counts, shares, labels, reasons), never interpretive ("this proves...", "AI is causing...").
- Every filter keeps a trace: rejected rows go to their own file with the reason, as `clean_news.py` does.

### 3. Do tell me your conjectures, in the session

I make the decisions, and I want your reading of the data to base them on. So in the conversation, speak freely:

- what you think the results suggest, and how sure you are
- other problems or weak signals the data hints at, even off-topic for the current assignment: noticing these is the point of strategic scanning
- what could make the result misleading (sampling bias, source bias, a rule that is too strict or too loose)
- what you would check next

Mark it clearly as your conjecture, separate from what the script measured. If I decide to act on one, it then goes into a script as an explicit, named, adjustable rule, not as a silent assumption.

### 4. Explain the structure of every script you write or change

I am learning Python. After each new script or significant change, give me a short, simple summary in the session:

- what goes in and what comes out (files, columns)
- the parts of the script in the order they run: constants at the top, each function in one line, then `main()`
- any Python idea that may be new to me, in one or two plain sentences (e.g. what a `set` is for, what `if __name__ == "__main__":` does)
- the commands to run it, with the options worth knowing

Keep it short and plain. No need to walk through every line.

## Script conventions

Follow the existing scripts:

- module docstring at the top: what the script does, its rules, and an `Examples:` block of commands
- constants in CAPITALS at the top, each with a comment saying why it is there
- small functions with a one-line docstring, then `main()` with `argparse`, then `if __name__ == "__main__":`
- `pathlib.Path` for files, `pandas` for tables, input and output paths as `--in` / `--out` options defaulting to `data/`
- print a short summary at the end of a run (rows in, rows out, where the file was saved)
- plain English in comments and docstrings, simple code over clever code
